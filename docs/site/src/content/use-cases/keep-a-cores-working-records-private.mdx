## In short

A core's own records of the work are rarely the requester's business. A Sanger plate holds
samples from several projects; a run folder lists them all; an analyst's notes say which reaction
was set up again and why. With this setup the core keeps all of that in its own project, and sends
back a separate, deliberate record for each tube:

- **A work item** is the core's private record of its work on a request: its own priority, the
  date it's scheduled, the instrument, internal notes and where the work is. Only the core's
  project can keep or refer to it, even for someone who is in both projects.
- **Files the core uploads** stay in its project. The requester can read a file only once a
  delivered result carries it.
- **A deliverable for each tube** is what goes back, with that tube's report and traces alone.

## What stays and what goes

<div class="table" tabindex="0" role="region" aria-label="What the core keeps and what goes back">
  <table>
    <caption class="sr-only">What the core keeps and what goes back</caption>
    <thead>
      <tr><th scope="col">Record</th><th scope="col">The core's project</th><th scope="col">The project that asked</th></tr>
    </thead>
    <tbody>
      <tr><td>The request, with the core's fields: status, priority, scheduled date, analyst, service notes</td><td>Reads it and sets its own fields</td><td>Owns it; reads the core's fields</td></tr>
      <tr><td>A work item, with its own priority, schedule, instrument and notes</td><td>Keeps it</td><td>Never sees it</td></tr>
      <tr><td>A file uploaded to the core's Files</td><td>Keeps it</td><td>Reads it only if a delivered deliverable carries it</td></tr>
      <tr><td>A deliverable</td><td>Keeps it until it's delivered</td><td>Sees it once it's delivered, for good</td></tr>
    </tbody>
  </table>
</div>

A work item's priority is the core's own, with a High between Routine and Urgent; the request's
priority, Routine or Urgent, is the one the requester reads.

## What Iki checks

- A work item refers to a request sent to the core's project, and no other project can keep it or
  refer to it.
- Its status moves Queued, Scheduled, Running, Done in that order, each set by an Analyst, or it's
  Cancelled with a reason while the work is still pending or running.
- A work item has no release: nothing makes it go back to the project that asked.

Every change to a work item is a revision of it, with who, through what and when: see
[What Iki keeps of every record](/concepts/what-iki-keeps-of-every-record/).
