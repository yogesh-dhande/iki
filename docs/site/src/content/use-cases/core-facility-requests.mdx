## In short

A sequencing core serves three research projects. With this setup:

- Requests arrive at the core in one queue, each with the tubes and the sequencing its project
  asked for, and the core's coordinators hear of each one as it arrives.
- The core sees exactly what was sent with a request, and nothing else of the project's.
- Each project sees only its own requests.
- Results come back attached to the request, one for each tube, and every change to either is
  kept in its history.

## What Iki records along the way

- Every change to a request or a result is a revision: who made it, through what, when, and which
  values changed. Earlier values stay in the record's history.
- A declined or withdrawn request keeps the reason it was given.
- Each record's audit trail can be exported as CSV.

## Variations of the workflow

- Require a signed review before a result goes back: add a signature to the deliverable's Returned
  state, as the example plugin's
  [ResearchCoreDeliverable](/reference/plugins/example-lims/#ResearchCoreDeliverable) does.
- Require signatures by the analyst, a reviewer and QA in turn: follow the plugin's
  [QCCoreDeliverable](/reference/plugins/example-lims/#QCCoreDeliverable).
- Let analysts start work without acceptance: drop Accepted from the request's states and from the
  analyst's [assignment](/reference/plugin-spec/field/#assignment).
- Take requests from a LIMS the lab already has: add an action that reads them through its API and
  a trigger that runs it on a schedule, as the plugin's
  [import_from_lims](/reference/plugins/example-lims/#import_from_lims) does for proteins.
- Charge each request to a cost centre: add a required cost centre field to the request type.
