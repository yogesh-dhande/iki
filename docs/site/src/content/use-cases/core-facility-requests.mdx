## In short

A sequencing core serves three research projects. With this setup:

- Requests arrive at the core in one queue, each with the tubes and the sequencing its project
  asked for, and the core's coordinators hear of each one as it arrives.
- The core sees exactly what was sent with a request, and nothing else of the project's.
- Each project sees only its own requests, and none of the core's own records of the work.
- Results come back attached to the request, one for each tube, and the request can't be closed
  until every tube has one.

The same request types serve any team asking another for work: a lot sent for testing, a protein
to be produced, data to be analysed.

## From the request to its results

Lena Fischer, in the AAV capsid engineering project, needs six miniprep clones checked by Sanger
sequencing. At the sequencing core, Sam Adeyemi coordinates, Maya Okafor runs the sequencer and
Tomás Herrera reviews what goes back.

## Variations of the workflow

- Return everything the core records, and keep no records of its own:
  [Return everything a core records to the project that asked](/use-cases/return-everything-to-the-requesting-project/).
- Keep the core's working records, raw data and notes in its own project, and send back only the
  results: [Keep a core's working records private](/use-cases/keep-a-cores-working-records-private/).
- Run the core with one person, who accepts, does and delivers the work:
  [Run a core facility with one person](/use-cases/run-a-core-facility-with-one-person/).
- Have a coordinator order the core's work and book its instruments, and analysts do it:
  [Schedule a core's work across several people](/use-cases/schedule-a-cores-work-across-several-people/).
- Require a signed review before a result goes back: use the
  [Research request](/reference/plugins/requests/#ResearchRequest) and
  [Research deliverable](/reference/plugins/requests/#ResearchDeliverable), where a Reviewer signs
  each deliverable Signed off.
- Require signatures by the analyst, a reviewer and QA in turn: use the
  [QC request](/reference/plugins/requests/#QCRequest) and
  [QC deliverable](/reference/plugins/requests/#QCDeliverable), whose result goes back when QA
  signs it Released.
- Take requests from a LIMS the lab already has: add an action that reads them through its API and
  a trigger that runs it on a schedule, as the example LIMS connector's
  [import_from_lims](/reference/plugins/lims-connector-example/#import_from_lims) does for proteins.
- Charge each request to a cost centre: write a request type of the lab's own that extends Plain
  request and adds a required cost centre field.
- Let analysts start work without acceptance: write a request type of the lab's own with states
  that leave out Accepted. A type that extends Plain request keeps its states.
