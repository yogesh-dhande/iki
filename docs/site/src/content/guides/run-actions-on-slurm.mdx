A Slurm cluster runs Iki's container-tier actions through a worker on its login node. The worker
leases Iki's jobs, stages each one on the cluster's shared file system and submits it with
`sbatch`. On the job's node, the job runs in its plugin's image under Apptainer. This page is for
the cluster's administrators and the Iki Compute admin who set it up together.

## What the cluster needs

- **A login node**, or any submit host, that reaches the Iki server and the deployment's object
  storage over HTTPS. It needs Slurm's `sbatch`, `squeue`, `sacct` and `scancel`, Apptainer 1.2 or
  later and [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) 2.x, and it
  must reach the registries the deployment's images come from.
- **A shared file system** that the compute nodes mount at the same path as the login node, such
  as `/scratch/iki`. It holds each job's inputs, outputs and log while the job runs, and the images
  as SIF files. Plan for the largest images, plus the inputs and outputs of the most jobs you let
  run at once.
- **Apptainer on every compute node**, at the same path as on the login node. GPU nodes need the
  NVIDIA driver: jobs that ask for GPUs run with `--nv`.
- **A service account**: a Unix user the worker runs as, which may submit to the partitions and
  accounts Iki uses. Its home directory keeps the worker's token. Every Iki job runs as this user.
- **Accounting** (slurmdbd). Without it, Iki still learns each job's exit status, but not what the
  job used, so it can't price the job, and preempted or failed nodes look like lost jobs. With
  `AccountingStoreFlags=job_comment` in `slurm.conf`, `sacct` also keeps each job's comment,
  `iki:<job>`, which finds the Iki job a Slurm job ran.
- **The egress proxy, if actions reach the internet or call outside APIs.** Compute nodes reach
  the deployment's egress proxy at the template's `egress_proxy_url`, usually a forwarded port on a
  host the nodes can reach. Without it, Iki refuses those actions on the cluster, and never runs
  them unproxied.

Compute nodes need no network to Iki or object storage.

## Templates

A Slurm template places jobs on one partition of one cluster. It's a `ComputeTemplate` with
`provisioner: slurm`, in the deployment's `compute.yaml`, which is reviewed and deployed like code
([Configure a deployment's plugins and compute](/guides/configure-plugins-and-compute/)):

```yaml
apiVersion: iki/v1
kind: ComputeTemplate
name: hpc-gpu
provisioner: slurm
capacity:
  cpu: 64
  memory: 512Gi
  gpu: { count: 4, memory: 80Gi, model: A100 }
slurm:
  cluster: hpc1 # Iki's name for the cluster; workers register for it
  partition: gpu
  qos: normal # optional
  account: rd-shared # optional: the account for projects without their own
  constraint: a100 # optional: --constraint, the node features it needs
  gpu_type: a100 # optional: --gpus=a100:<n>
  max_walltime: 2d # the partition's time limit
  egress_proxy_url: http://iki-proxy.hpc.example.com:3128 # optional
price: { per_cpu_hour: 0.02, per_gpu_hour: 1.10, per_memory_gib_hour: 0.001, currency: USD }
limits: { max_concurrent: 50 }
```

- [`capacity`](/reference/plugin-spec/compute-template/#capacity) is the most one job may ask for
  there.
- [`limits.max_concurrent`](/reference/plugin-spec/compute-template/#limits.max_concurrent) caps
  how many of the template's jobs are in the cluster at once, waiting or running.
- [`price`](/reference/plugin-spec/compute-template/#price) is what Iki charges a project's budget
  for each hour of what Slurm allocated. Leave it out to show no cost.

Bind environments to the template like any other, in the order they're tried:

```yaml
apiVersion: iki/v1
kind: EnvironmentBinding
environment: acme/structures.colabfold
templates:
  - { template: hpc-gpu, priority: 0 }
  - { template: gke-gpu, priority: 1 }
```

`iki deploy build` refuses a template or binding the cluster can't run: a `per_hour` price,
`kubernetes` settings, warm machines, an environment with volumes, or a binding none of whose
templates allows an action's timeout within its `max_walltime`. It warns of an action that reaches
the internet, or calls outside APIs, when its binding has only templates without an
`egress_proxy_url`. Wherever such an action would be launched, the server says why it can't run
there.

Templates are shown, read-only, under **Compute → Slurm**.

## Accounts per project

Each project's jobs are charged to a Slurm account on each cluster. Under **Compute → Slurm**, a
Compute admin sets each project's account, or through the API with
[`PUT /compute/slurm/{cluster}/accounts/{project_id}`](/reference/api/put-compute-slurm-cluster-accounts-project-id/).
A project without one uses its template's `account`. If the template has none, the project's runs
fail with a message saying who can set it. The audit log records each change, with the account
before and after (`slurm_account.changed`).

The service account must be a member of every account it charges:

```sh
sacctmgr add user iki-svc account=<account>
```

## Set up the login node

1. **Register the worker.** Under **Compute → Workers**, a Compute admin makes a container-tier
   registration token, with **Slurm cluster** set to the cluster's name (`hpc1`). On the login
   node, as the service account:

   ```sh
   iki-worker register --url https://iki.example.com --token iki_wreg_… --name hpc1-login1
   ```

   It keeps the worker's token in `~/.config/iki/worker.json`, readable only by the service
   account. Keep that home directory off the shared file system if you can.

2. **Make the work directory**, readable by the service account only:

   ```sh
   install -d -m 0700 -o iki-svc /scratch/iki
   ```

   The worker keeps every job's files in it, and any other user who could read it would see
   inputs and results. Check that the file system honours modes: some parallel file systems need
   an ACL or a project directory instead.

3. **Run it as a service**, with a systemd unit such as:

   ```ini
   [Unit]
   Description=Iki worker for the hpc1 Slurm cluster
   After=network-online.target

   [Service]
   User=iki-svc
   Environment=IKI_SLURM_WORK_DIR=/scratch/iki
   Environment=IKI_SLURM_MAX_JOBS=200
   ExecStart=/opt/iki/bin/iki-worker start
   Restart=always
   KillSignal=SIGTERM
   TimeoutStopSec=60

   [Install]
   WantedBy=multi-user.target
   ```

| Variable                 | Default                      | What it sets                                                                    |
| ------------------------ | ---------------------------- | ------------------------------------------------------------------------------- |
| `IKI_SLURM_WORK_DIR`     | none: it's required          | The shared directory jobs are staged in. Setting it puts the worker in Slurm mode |
| `IKI_SLURM_IMAGE_CACHE`  | `$IKI_SLURM_WORK_DIR/images` | Where images are kept as SIF files                                              |
| `IKI_SLURM_MAX_JOBS`     | 100                          | The most jobs this worker holds at once, up to 1,000                            |
| `IKI_SLURM_POLL_SECONDS` | 15                           | How often it asks `squeue` about its jobs                                       |
| `IKI_SLURM_BIN`          | on `PATH`                    | The directory of `sbatch`, `squeue`, `sacct` and `scancel`                      |
| `IKI_APPTAINER`          | `apptainer`                  | Apptainer, at the same path on the compute nodes                                |
| `IKI_COSIGN`             | `cosign`                     | cosign                                                                          |

The worker won't start if its registration and its settings disagree: `IKI_SLURM_WORK_DIR` set on
a worker that isn't registered for a cluster, or unset on one that is. It keeps its token across
restarts, so it doesn't take a one-off `IKI_WORKER_TOKEN`.

Like any self-hosted worker, it fetches the code of the plugins the deployment installs, at their
commits, and runs their jobs. A development server's plugins from local directories aren't sent
to it: set `IKI_PLUGINS_DIR` to their code instead.

A second login node can run a second worker with the same work directory and image cache. The
server keeps to the template's `max_concurrent` across both.

## What a job does

For each job, the worker:

1. makes the job's directory, `$IKI_SLURM_WORK_DIR/jobs/<job>`, with mode 0700;
2. downloads the job's inputs, and copies in its plugin's code;
3. checks the image's signature with `cosign verify`, against the signers the deployment trusts
   (the chart's `containerTier.imagePolicy`), then pulls the image by its digest into the image
   cache, unless it's there already;
4. writes `step.json`, `secrets.json` (mode 0600) and `job.sh`, and submits it:

   ```sh
   sbatch --parsable --export=NONE --no-requeue --nodes=1 --ntasks=1 \
     --job-name=iki-<run>-<attempt> --comment=iki:<job> \
     --partition=gpu --account=<project's> --cpus-per-task=… --mem=… \
     --gpus=a100:1 --time=… --output=<dir>/log job.sh
   ```

5. follows the job in `squeue`, renews its lease, streams its log to the run's page, and cancels
   it with `scancel` as soon as the run is cancelled;
6. once the job leaves the queue, reads how it ended and what it used from `sacct`, uploads its
   results, and removes its directory.

On the node, `job.sh` runs `$IKI_SLURM_WORK_DIR/bin/iki-worker-<version> slurm-step <dir>`, which
reads and deletes `secrets.json` and runs:

```sh
apptainer exec --containall --cleanenv --home <dir>/home --bind <dir> [--nv] <image>.sif <command>
```

The step writes what the command prints to `<dir>/log`, with the job's secrets and its proxy
credentials as `***`, so the log file never holds them. It passes on the signals Slurm sends, and
exits as the command did. The worker's own token is never in the job's directory or its
environment.

To find Iki's jobs on the cluster:

```sh
squeue -u iki-svc -o '%i %j %k %T %R'      # %k is the comment: iki:<job>
sacct -u iki-svc --format=JobID,JobName%30,Comment%45,Account,State,Elapsed,AllocTRES%60
```

The run's page shows the same Slurm job ID, its state, and why it's waiting.

## Restarts, upgrades and draining

- **Restarting the worker** leaves its jobs running. On SIGTERM it stops leasing and lets go of
  its jobs. When it starts again, it picks each job up from its directory's `slurm.json`, and
  carries on with its log from where the run's page has it (`log.json` notes how far it got). A
  job's lease lasts ten minutes without the worker. If the worker is away longer, the server gives
  up on the job, and the worker cancels it and removes its directory when it's back. While the
  server can't answer, or answers that it's busy, the worker asks again until it does, and the job
  runs on meanwhile.
- **Upgrading** works as for any self-hosted worker: it updates itself to the release the server
  wants when it holds no jobs, or you install the new binary and restart the service. Running jobs
  keep the version they started with, under `bin/`.
- **Draining a partition** for maintenance: lower the template's `max_concurrent`, or bind its
  environments elsewhere, and deploy. Jobs already submitted run to the end. Jobs Slurm preempts,
  or whose nodes fail, end as interrupted and are retried if their action allows it.
- **Taking a cluster off Iki**: revoke its workers under **Compute → Workers**. Each worker cancels
  its jobs and stops.

## When something's wrong

| What the run's page says                                                         | What to check                                                                                                                  |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Waiting for the hpc1 cluster's worker: none is online                            | The worker service on the login node, and its log (`journalctl -u iki-worker`)                                                 |
| Waiting for room on the hpc1 cluster                                             | The template's `max_concurrent`, and the jobs already in the cluster                                                           |
| Waiting in the cluster's queue (reason: `Priority`, `QOSMaxJobsPerUserLimit`, …) | Slurm's own queue: the reason is `squeue`'s                                                                                    |
| The cluster refused the job: …                                                   | The partition, account and QOS: `sacctmgr show assoc user=iki-svc`                                                             |
| … has no Slurm account on hpc1                                                   | The project's account under Compute → Slurm                                                                                    |
| Its image … isn't signed by anyone the deployment trusts                         | The chart's `containerTier.imagePolicy`, and that cosign on the login node reaches the registry and Sigstore's public instance |
| Slurm stopped it: it used more than the … of memory it asked for                 | The environment's memory, in the plugin                                                                                        |
| Slurm stopped it at its time limit                                               | The action's timeout, and the partition's `max_walltime`                                                                       |
| Its Slurm job … was cancelled on the cluster by user …                           | Someone cancelled it outside Iki; it's retried if its action allows it                                                         |

The worker logs one JSON line per event to stderr, with the job and its Slurm job's ID.

## Usage by person

Every job runs as the service account, and is charged to its project's account. The job's
comment, `iki:<job>`, ties it to its Iki run, and the run's audit trail names the person who
launched it. Join `sacct` to Iki's audit log to report usage by person.
